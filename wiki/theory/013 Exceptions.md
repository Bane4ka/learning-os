# Exceptions (исключения)

> [!info] Что это
> Исключение — объект, который Python создаёт в момент ошибки времени выполнения и "выбрасывает" вверх по стеку вызовов. Если по пути никто его не поймал — программа аварийно завершается, и ты видишь traceback. `try/except` — способ поймать этот объект и решить, что делать, вместо аварийного завершения.

---

## Иерархия исключений — не всё "ValueError"

Все встроенные исключения — классы, наследующиеся от `BaseException`. Практически важная часть дерева:

```
BaseException
 └── Exception                 ← почти всё, что ты ловишь, наследуется отсюда
      ├── ValueError            — правильный тип, неправильное значение: int("abc")
      ├── TypeError              — операция применена к несовместимому типу: "2" + 2
      ├── KeyError               — несуществующий ключ словаря: d["нет"]
      ├── IndexError             — несуществующий индекс: [1,2,3][10]
      ├── ZeroDivisionError       — деление на 0
      ├── AttributeError          — обращение к несуществующему атрибуту/методу: "abc".push()
      ├── FileNotFoundError       — открытие несуществующего файла (увидишь в [[Files]])
      ├── ImportError / ModuleNotFoundError — модуль не найден
      └── StopIteration           — исчерпан итератор (увидишь в генераторах)
```

Почему это важно: `except Exception:` поймает **вообще любую** ошибку из этого дерева — не только ту, что ты предвидел. `except ValueError:` поймает только `ValueError` и его подклассы. Чем точнее тип — тем меньше шанс случайно скрыть баг, который ты не собирался прятать.

`BaseException` шире `Exception` — включает ещё `SystemExit`, `KeyboardInterrupt` (Ctrl+C). Голый `except:` (без указания типа вообще) ловит и их тоже — из-за этого твоя программа перестанет реагировать даже на Ctrl+C. Это ещё одна причина, почему голый `except:` считается плохой практикой, а не только "менее точной".

## Полный синтаксис и порядок выполнения

```python
try:
    x = int(input("Число: "))
except ValueError:
    print("Не число")
else:
    print(f"Принято: {x}")
finally:
    print("Блок завершён")
```

Порядок выполнения по шагам:

1. Выполняется `try`
2. Если ошибок не было → выполняется `else` (может отсутствовать) → затем `finally`
3. Если была ошибка, совпавшая с одним из `except` → выполняется этот `except` → затем `finally`
4. Если была ошибка, ни с одним `except` не совпавшая → `finally` всё равно выполнится, а затем ошибка полетит дальше вверх по стеку — `try/except` её не проглотит молча, если тип не совпал

`finally` — единственный блок, который выполнится **в любом случае**, даже если внутри `try` или `except` был `return`. Практическое применение: закрытие файла, соединения с БД, освобождение ресурса — вещи, которые обязаны произойти независимо от исхода.

> [!tip] Зачем нужен `else`, если код можно просто дописать после `try`
> Код в `else` выполнится, только если `try` прошёл **без ошибок**. Если написать этот же код просто следующей строкой после `try/except` (не внутри `else`) — он тоже выполнится после `except`, даже если там была ошибка и `except` её обработал. `else` — способ явно сказать "это выполняется только при успехе", а не "выполняется всегда после блока".

## Несколько типов в одном except

```python
try:
    ...
except (ValueError, TypeError):
    print("Проблема с типом или значением")
```

Круглые скобки — кортеж типов, один обработчик на оба случая. Если нужна **разная** реакция — используй раздельные `except` блоки, порядок важен (Python берёт первый подходящий сверху вниз).

## EAFP vs LBYL — философия Python

Два подхода к одной и той же задаче — "избежать ошибки":

**LBYL** (Look Before You Leap — "посмотри, прежде чем прыгнуть"):
```python
if key in dictionary:
    value = dictionary[key]
else:
    value = "нет значения"
```

**EAFP** (Easier to Ask Forgiveness than Permission — "легче попросить прощения, чем разрешения"):
```python
try:
    value = dictionary[key]
except KeyError:
    value = "нет значения"
```

Python исторически тяготеет к EAFP — это идиоматичный стиль. Причина не только вкус: LBYL иногда содержит **race condition** (между проверкой `if key in dict` и использованием `dict[key]` кто-то теоретически может успеть изменить словарь — в многопоточном коде это реальная проблема) и часто требует **двух обращений** к структуре данных вместо одного (`in` — это один проход/хэш, потом `[]` — ещё один). EAFP делает одно обращение и обрабатывает исход.

Это прямая связь с твоим заданием — сравнить `.get()` из [[012 Dictionaries]] и `try/except KeyError`: оба рабочие, но `try/except` — более "питонический" выбор в общем случае, `.get()` короче для простого дефолтного значения.

## raise — выбросить исключение самому

```python
def set_age(age):
    if age < 0:
        raise ValueError("Возраст не может быть отрицательным")
    return age
```

Ты не обязан ждать, пока Python сам наткнётся на ошибку — можно явно сообщить о невалидном состоянии. Это основа валидации данных в реальном коде (в том числе в API, которые тебя ждут в [[018 Backend (заготовка)|Backend]]).

### Повторный выброс — `raise` без аргумента внутри except

```python
try:
    risky_operation()
except ValueError:
    print("Залогировали проблему")
    raise   # пробрасываем ту же ошибку дальше, после того как что-то с ней сделали
```

Полезно, когда нужно отреагировать на ошибку (залогировать, откатить транзакцию), но при этом не скрывать её — пусть вызывающий код тоже узнает, что что-то пошло не так.

## Частые ошибки

> [!warning] Голый `except:` без типа
> Ловит вообще всё, включая `KeyboardInterrupt` и опечатки в коде (`NameError` из-за опечатки в имени переменной) — маскирует баги вместо их исправления.

> [!warning] Слишком широкий `try`-блок
> ```python
> try:
>     category = input('Категория: ')
>     amount = int(input('Сумма: '))
>     add_expense(expenses, category, amount)
>     show_totals(expenses)
> except ValueError:
>     print('Ошибка')
> ```
> Если упадёт `add_expense` по совсем другой причине — непонятно, где именно, потому что весь блок из 4 строк считается "одним местом". Оборачивай в `try` **минимальный** участок, который реально может упасть.

> [!danger] Использовать исключения для обычной логики ветвления
> ```python
> try:
>     x = my_list[10]
> except IndexError:
>     x = None
> ```
> Если ты точно знаешь, что индекс часто будет выходить за границы (это не "исключительная" ситуация, а обычный сценарий) — быстрее и понятнее явная проверка `if len(my_list) > 10`. Исключения относительно недороги, когда их **не** выбрасывают, но каждый реальный `raise` — заметные накладные расходы. Использовать их вместо `if` там, где ошибка — не редкость, а норма, считается анти-паттерном.
